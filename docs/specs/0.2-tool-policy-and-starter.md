# noxguard 0.2: a tool policy for agents and a Spring Boot starter

Status: approved by Marcus (2026-10-06), with the dependencies below and the input classifier moved to 0.3.

## Why

**Tool policy.** 0.1 gave agents three loose pieces: `ProposalGate` (hold a proposed action until the answer is not a refusal), `ToolBudget` (cap calls per answer) and `StrictSchema` (make a tool schema strict). An app still has to write, by hand and in the right order, the rules that decide whether a tool call the model asked for may run: is this tool allowed at all? are the arguments acceptable? has the answer used its calls? does this tool change something outside, so a person must confirm first?

That is exactly what Nox's agent does in its tool loop, spread across a few functions: an unknown tool gets an error back ("unknown tool. Available: ..."), arguments are validated in code (strict mode cannot carry `maxLength` or patterns, as `StrictSchema` already says), the fourth call gets "tool limit reached; answer now", the message tool only proposes a draft that the visitor confirms, and only some arguments are written to logs.

0.2 turns those rules into one declarative object, `ToolPolicy`, checked before every tool call. It is to an agent's tools what Spring Security is to a web app's endpoints: deny by default, a rule per tool, and a decision the app can act on (run, refuse with a reason the model can read, or ask the user).

This is OWASP LLM06 (Excessive Agency) handled in code: the model can ask for anything; the policy decides what runs.

**Spring Boot starter.** The example app wires the guards in a 60-line `@Configuration` class. Every Spring Boot app would copy it. A starter turns that into properties, with safe defaults and a startup failure when a setting is unsafe (a short history secret), the way Spring Boot apps expect.

## The tool policy (package `agent`, in `noxguard-core`)

```java
ToolPolicy policy = ToolPolicy.builder()
    .tool("search_site")                                         // read-only: runs when asked
    .tool("get_case_study", t -> t
        .arg("slug", ArgRule.matches("^[a-z0-9-]{1,60}$"))       // checked in code, every call
        .logArgs("slug"))                                        // only this argument goes to logs
    .tool("send_message", t -> t
        .confirm()                                               // a side effect: the user confirms first
        .arg("email", ArgRule.maxLength(120))
        .arg("body", ArgRule.maxLength(2000))
        .maxCalls(1))                                            // per answer
    .maxCalls(3)                                                 // all tools, per answer
    .build();                                                    // validates; anything not listed is denied

ToolSession session = policy.session();                         // one per answer, like StreamGuard
ToolDecision decision = session.decide(new ToolCall("get_case_study", args));

switch (decision) {
    case ToolDecision.Run run       -> result = execute(run.call());
    case ToolDecision.Confirm c     -> gate.hold(draftFrom(c.call()));      // ProposalGate, as in 0.1
    case ToolDecision.Deny deny     -> result = deny.messageForModel();     // e.g. "Error: unknown tool. Available: ..."
}
```

Rules:

- **Deny by default.** A tool that is not declared is denied (`Deny` with reason `UNKNOWN_TOOL`). The message for the model lists the declared tools, as Nox does, so the model can recover.
- **Arguments.** `args` is a `Map<String, Object>` (the core has no JSON dependency; the app parses the model's JSON). Each declared rule runs on every call. Built-in rules: `required()`, `matches(pattern)` (whole value), `maxLength(n)`, `oneOf(values)`, `type(String/Number/Boolean)`. An app rule is a small interface returning `Optional<String>` (the violation). A violation gives `Deny` with reason `ARGUMENT` and which argument, never echoing the value back (it may hold what the attacker wanted to smuggle).
- **Undeclared arguments**: denied by default (`ARGUMENT`), matching strict tool calling (`additionalProperties: false`). A tool can opt out with `.allowOtherArgs()`.
- **Limits.** `maxCalls` per tool and in total, per answer. Over the limit: `Deny` with `LIMIT`, message "tool limit reached; answer now", and `session.nextChoice()` turns to `NONE`, like `ToolBudget`. A denied call does not count against the limit; a confirmed one does.
- **Confirmation.** A tool marked `confirm()` never gets `Run`. It gets `Confirm(call)`, which the app hands to a `ProposalGate`: the proposal is shown only if the final answer is not a refusal, and the side effect happens only when the user confirms. The policy cannot run a confirmed tool by itself; that would defeat the point.
- **Logs.** `decision.loggableArgs()` returns only the arguments listed in `logArgs` (default: none). Nox logs the case slug and the message subject, never the message.
- **Sealed results.** `ToolDecision` is `sealed` (`Run`, `Confirm`, `Deny`) and `Deny.reason()` is an enum (`UNKNOWN_TOOL`, `ARGUMENT`, `LIMIT`), so a `switch` covers every case and a log can count reasons.
- **State.** `ToolPolicy` is immutable and shared; `ToolSession` holds the counts of one answer and is not thread-safe (stated in the Javadoc, as for `StreamGuard`).
- `ToolBudget` stays for apps that only want the cap; `ToolPolicy` uses the same semantics.

Parity with Nox: every rule above is something Nox's tool loop does today. The tests port Nox's agent cases (unknown tool, limit at the fourth call, bad slug, the message tool only proposing) and add adversarial ones (path-like slugs, very long arguments, the value never appearing in the model message).

## Input classifier port (promised in 0.1 for 0.2): moved to 0.3

The 0.1 spec listed, for 0.2, an `InputClassifier` port with explicit fail-open or fail-closed behavior: when the classifier (a remote model, like Jev in Nox) times out or errors, does the message pass or get blocked? Nox fails open (the message passes, and the output guards still run).

- **Option A, include it in 0.2.** Small: an interface, a result with scores, and a combinator with timeout and an explicit `FailureMode` (no default, so the app must choose).
- **Option B, move it to 0.3.** Keeps 0.2 about agents and Spring; 0.3 can bring it with a Spring AI advisor.

Decision (2026-10-06): **B**. 0.2 already has one new concept (the tool policy) and one new module (the starter). The 0.1 spec now points to 0.3.

## Spring Boot starter: `noxguard-spring-boot-starter` (new module)

One module with the auto-configuration and the starter together (small library, one jar to add). Depends on `noxguard-core`; uses `noxguard-reactor` only when it is on the classpath.

```yaml
noxguard:
  stream:
    leak-markers: ["<context>", "You are Acme's assistant"]
    max-chars: 1200
  links:
    allow: ['^([a-z0-9-]+\.)*example\.com$']
  data:
    reserved-tags: [context, question, tool]
  history:
    secret: ${NOXGUARD_HISTORY_SECRET}       # at least 32 bytes
  refusal: "I can only answer questions about this site."
  tools:
    max-calls: 3
    allow:
      get_case_study:
        args:
          slug: '^[a-z0-9-]{1,60}$'
        log-args: [slug]
      send_message:
        confirm: true
        max-calls: 1
```

Beans, each `@ConditionalOnMissingBean` so the app can replace any of them:

| Bean | From | When |
| --- | --- | --- |
| `LinkPolicy` | `noxguard.links.allow` | always (empty list: no link allowed) |
| `DataEnvelope` | `noxguard.data.reserved-tags` | always |
| `HistorySigner` | `noxguard.history.secret` | when the secret is set |
| `StreamGuards` (a factory: one new `StreamGuard` per answer) | `noxguard.stream.*` | when leak markers are set |
| `ReactorGuard` | the factory, links and refusal | when `noxguard-reactor` is on the classpath |
| `ToolPolicy` | `noxguard.tools.*` (patterns only; code rules need a bean of their own) | when tools are declared |

Fail fast at startup, with a clear message:
- `noxguard.history.secret` shorter than 32 bytes. No random fallback in the starter (the example app has one for demos and logs a warning; a library that silently invents a secret would break signed history on every restart in production). An app that wants the demo behavior sets `noxguard.history.random-secret-for-development=true` and gets the same warning.
- An invalid regex in `links.allow` or a tool argument.
- A tool both listed and empty of meaning (for example `confirm: true` and `max-calls: 0`).

Configuration metadata is generated, so IDEs autocomplete the properties and show their Javadoc.

The example app moves to the starter: its `GuardConfiguration` shrinks to the beans that are really app-specific (the chat policy and the use case), and it gains a tool declared through properties. Its noxeval suite gets cases for the policy (a forbidden tool, a bad argument, the message tool only proposing).

_Discarded_: two modules (`-autoconfigure` and `-starter`), the split Spring recommends for large projects. For two small jars it doubles the release work with no gain for users; the split can come later without breaking anyone, since the starter's coordinates stay. _Discarded_: a Spring AI `StreamAdvisor` in this release; it can come with the input classifier.

## Versions and compatibility

- `0.2.0`: new types and a new module, no change to 0.1 signatures. An app on 0.1 upgrades by changing the version.
- The starter targets Spring Boot 4.1 (as the example app); the auto-configuration registration and test utilities are checked against the Boot 4 docs at implementation, since Boot 4 reorganized its auto-configuration modules.
- Core and reactor still compile with `--release 21`; the starter too (Boot 4 runs on 17+).

## Known limits (stated in the README)

- The policy decides on the call the model asked for; it does not make the tool itself safe. A tool that can delete data needs its own authorization in the system it touches.
- Argument rules check shape, not intent: `slug` matching a pattern does not mean the user may see that case. Authorization of the data belongs to the app.
- `Confirm` relies on the app showing the proposal and waiting for the user. The policy cannot see the UI.

## Out of scope for 0.2

- Input classifier port (moved to 0.3).
- A Spring AI advisor and a LangChain4j adapter.
- Quotas across answers (they need storage).
