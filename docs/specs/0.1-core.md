# noxguard 0.1: deterministic guardrails for LLM chats and agents, in Java

Status: approved by Marcus (2026-10-04), with Java 21 as the target and 25 in CI. Implemented the same day; publishing to Maven Central is the last step.

## Why

An LLM chat that streams its answer has a problem most guardrail libraries skip: the text leaves the server in pieces. Checking the whole answer at the end means either buffering it (the user loses streaming) or letting a leak reach the screen before the check runs. In LangChain4j, output guardrails on a streaming call run once the stream is complete, with the partial responses buffered and replayed afterwards. Spring AI's `SafeGuardAdvisor` is a case-sensitive substring check against a word list, applied to the request.

Agents add a second problem: a model with tools can propose an action it should not, and a prompt rule only lowers how often that happens. The fix that held in production was in code, not in the prompt.

noxguard packages the guards that hold [Nox](https://marcusrdrigues.com), the public chat on the author's portfolio: a streaming output guard, a link allow list, data delimiting, signed history, an agent proposal gate and input views for a classifier. They were written in TypeScript for Nox and measured there with [noxeval](https://github.com/marcusrdrigues/noxeval): 47 of 47 cases, each asked three times, in the run of 2026-10-04. This is the Java port, for Spring AI, LangChain4j or plain Java apps.

**noxeval measures, noxguard enforces.**

## What it is and what it is not

- A small library of pure, deterministic functions. No network, no model, no runtime dependency in the core.
- Not a classifier. It does not decide whether a message is an attack; it gives a classifier better input (decoded views) and enforces what the app decides.
- Not a replacement for good design. The strongest guard in Nox is architectural: no tool can send anything, and the message recipient is fixed. The library makes the remaining layers cheap to add and easy to test.

## Design

**Clean Architecture for a library: ports and adapters, dependencies pointing inward.**

```
noxguard/                          Maven multi-module, groupId com.marcusrdrigues
├── noxguard-core/                 the guards; zero runtime dependencies, no framework
├── noxguard-reactor/              adapter: a Flux<String> stream guarded into Flux<GuardEvent>
└── examples/chat-spring-boot/     example app, not published; layered (domain, application, infrastructure, web)
```

- `noxguard-core` knows no framework. Adapters depend on the core, never the reverse. A LangChain4j adapter later is a new module, with no change to the core.
- `module-info.java` in each published module exports only the API packages; internals stay hidden.
- Results are sealed types and records (`sealed interface StreamStatus permits Open, Tripped, Capped`), not booleans or exceptions. No `null` in the public API: absent values are `Optional`.
- Immutable configuration through small builders that validate on `build()` (an empty marker list or a secret under 32 bytes fails fast with a clear message).
- Stateful guards (`StreamGuard`, `ProposalGate`, `ToolBudget`) belong to one answer and are **not thread-safe**; the Javadoc says so. Stateless ones (`LinkPolicy`, `DataEnvelope`, `HistorySigner`, `InputViews`) are immutable and safe to share.
- Javadoc on every public type and method; tests named after behavior.

**Java versions.** Compiled with `--release 21`, so apps on Java 21 or later can use it. CI builds and tests on Java 21 and 25 (the latest LTS). The example app requires 25. _Discarded_: requiring 25 for the library, which would cut out every app still on 21 for no gain in the code (records, sealed types and pattern matching in `switch` are all in 21).

**Build.** Maven. _Discarded_: Gradle, no gain here and one more tool to learn.

_Discarded_ for the whole design:
- **Each guard as a separate service.** The stream guard runs on every chunk, in microseconds; a network hop per chunk adds latency and a new failure mode ("the guard service is down: let the text through or block it?"). A library runs inside the app's process. A hosted service, if ever needed (say, a trained classifier), becomes an adapter behind a port.
- **One module with everything.** The core would carry Reactor and Spring for users who only want the history signer.
- **Porting the trained input classifiers** from Nox's fine-tuning study. On a fresh confirmation set, written after the rules were registered, the best one blocked 4 of 74 legitimate questions. Shipping a model that failed its own confirmation contradicts the project.

## The guards (v0.1)

Each one is a port of code that runs in Nox, with Nox's tests ported alongside so the behavior matches.

### 1. `StreamGuard` (package `output`)

Guards a streamed answer against prompt leaks and runaway length, without buffering it.

```java
StreamGuard guard = StreamGuard.builder()
    .leakMarkers(List.of("<context>", "You are Acme's assistant"))
    .maxChars(1200)
    .build();

String safe = guard.push(delta);   // what can be shown now ("" if nothing yet)
String rest = guard.end();         // what is left at the end of the stream
StreamStatus status = guard.status();  // Open | Tripped(marker) | Capped
String all = guard.received();     // full text received, for logs and final checks
```

Rules:
- The guard holds back the last `max(marker length) - 1` characters. A marker is therefore always seen whole before any of its characters is released.
- When a marker appears, the status becomes `Tripped(marker)`; `push` and `end` return `""` from then on. The app cancels the model call and replaces the answer with its refusal.
- When the answer goes past `maxChars`, the status becomes `Capped`; `end` returns `"…"` (or the trimmed rest plus `"…"`). The app can cancel the model call. An answer of exactly `maxChars` is released whole, without the mark (Nox marks it).
- A surrogate pair (an emoji, for instance) is never split between two releases.
- Markers are matched exactly (case-sensitive), as in Nox.

### 2. `LinkPolicy` (package `output`)

Finds links outside an allow list, the classic exfiltration route in RAG chats (a link or image with data in the URL).

```java
LinkPolicy links = LinkPolicy.allow(Pattern.compile("^([a-z0-9-]+\\.)*example\\.com$"));
List<ForeignLink> found = links.foreignLinks(answer);  // ForeignLink(kind: URL | MARKDOWN_IMAGE, value)
```

Rules: only explicit links count (`http://`, `https://`, `www.`, not glued to a letter or digit), so names like ASP.NET or Node.js are not taken for addresses; a link ends at any Unicode whitespace, as in JavaScript (Java's `\s` is ASCII-only, and a no-break space would otherwise join a foreign link to an allowed one); trailing punctuation is stripped; the value is lowercased; a link passes when the full value or its host matches an allowed pattern. Any Markdown image (`![...](`) is reported, allowed or not.

In Nox the check runs on the full text at the end of the stream; when it finds a link, the whole answer is replaced by the refusal. The stream adapter (item 7) does the same.

### 3. `DataEnvelope` (package `data`)

Wraps untrusted text (retrieved passages, tool results) as data before it goes into the prompt.

```java
DataEnvelope envelope = DataEnvelope.withReservedTags(Set.of("context", "question", "tool"));
String block = envelope.wrap("tool", Map.of("name", "get_case_study"), resultText, 4000);
// <tool name="get_case_study">\n...\n</tool>
```

Rules: the `<` of every reserved tag inside the text becomes `&lt;` (so the content can't close the block or open a fake one): opening or closing, any case, any kind of space before the name, and unfinished tags too (`<tool x=` with no `>`, which would otherwise swallow the real closing tag). One pass, so hostile input can't make it slow. (Changed during implementation; the draft removed whole tags, which an independent review broke three ways: a tag formed by removing another, an unfinished tag, and quadratic time on 100 KB of `<tool`. Nox has the first two gaps.) the text is cut at the limit with `\n[...]`; attribute values come from the app, not from the model, and are escaped anyway.

### 4. `HistorySigner` (package `history`)

Stops forged conversation history. The server signs each answer it sends; on the next request, assistant turns without a valid signature are dropped before reaching the model.

```java
HistorySigner signer = HistorySigner.hmacSha256(secret);      // secret: at least 32 bytes
String sig = signer.sign("answer:en", text);                   // Base64url
boolean ok = signer.verify("answer:en", text, sig);           // constant-time compare
List<Turn> kept = signer.keepSigned(history, "answer:en");    // Turn(role, content, Optional<sig>)
```

Rules (as in Nox):
- A user turn is kept; an assistant turn is kept only with a valid signature for that scope.
- When an assistant turn is dropped, the user turn right before it goes too (a question with no answer).
- A trailing user turn with no answer is dropped.
- The scope (`"answer:en"`) binds the signature to its context, so an answer signed for one locale or app does not verify in another.

### 5. Agent guards (package `agent`)

**`ProposalGate<T>`**: holds an action the model proposed (a draft message, an order) until the answer is complete, and releases it only if the final answer is not a refusal.

```java
ProposalGate<Draft> gate = ProposalGate.create();
gate.hold(draft);                                  // false if a proposal is already held
Optional<Draft> shown = gate.release(refused);     // empty when the answer was a refusal
```

This is the guard from Nox's "the model tried, the code said no" case: asked to email HR on the owner's behalf, the model proposed a message once in six attempts and then refused; the gate dropped the draft every time.

**`ToolBudget`**: caps tool calls per question.

```java
ToolBudget budget = ToolBudget.of(3);
boolean allowed = budget.tryUse();     // counts one call; false over the cap (answer it with an error, not a run)
ToolChoice next = budget.nextChoice(); // AUTO, or NONE once the cap is reached
```

**`StrictSchema`**: turns a JSON Schema (as `Map<String, Object>`, so the core has no JSON dependency) into the shape strict tool calling accepts: every object closed (`additionalProperties: false`), every property required (an optional one becomes nullable, `anyOf` with `null`, so the model sends `null` instead of inventing a value), and only the keywords strict mode accepts (`type`, `properties`, `required`, `additionalProperties`, `description`, `enum`, `items`, `anyOf`). Size limits that strict mode rejects (`minLength`, `maxLength`) are removed from the schema; they still have to be checked in code, and the Javadoc says so.

### 6. `InputViews` (package `input`)

Gives an input classifier the versions of a message an attacker hides.

```java
String clean = InputViews.normalize(message);       // NFKC, invisible characters removed, spaces collapsed
List<String> views = InputViews.decoded(message);   // decoded base64 runs, ROT13 segments, leetspeak
```

Rules (as in Nox): base64 runs of 16+ characters are decoded and kept only when the result reads as language; ROT13 is applied per segment and kept only when the flipped text has clearly more common words (Portuguese and English lists, as in Nox; the list is configurable); leetspeak is decoded when three or more words mix letters and digits. An ordinary question produces no views, so the classifier sees only the message.

### 7. `noxguard-reactor`: the stream adapter

```java
Flux<GuardEvent> guarded = ReactorGuard.guard(chatClient.prompt(q).stream().content(), guardFactory, links, refusal);
// GuardEvent: Delta(text) | Replace(text) | Done(status)
```

- One `StreamGuard` per subscription (`Flux.defer`), never shared between answers.
- `Delta` for each safe piece; on a trip, the upstream is cancelled and a `Replace(refusal)` is emitted; at the end, the rest is released, or the answer is replaced when `LinkPolicy` finds a foreign link or the answer is empty.
- The app maps the events to its wire format (Nox uses one JSON line per event). A client that already showed some text must handle `Replace`.

Depends on `reactor-core` only, not on Spring AI, so it works with WebFlux, Spring AI, or anything that produces a `Flux<String>`. _Discarded_: naming it `noxguard-spring-ai`; nothing in it is specific to Spring AI. A Spring AI `StreamAdvisor` can come later if a real app needs the guard inside the advisor chain.

## Example app and evaluation

`examples/chat-spring-boot` (Spring Boot 4 and Spring AI 2.0; exact versions pinned and checked against their docs at implementation) is a small chat with the full pipeline: signed history in, delimited passages, guarded stream out, a proposal tool behind the gate.

- **Scripted model by default.** A fake `ChatModel` streams prepared answers, including leaks split across chunks, a foreign link and an action proposal followed by a refusal. No API key, no cost, same result every run.
- **A noxeval suite runs against it in CI** over HTTP, the same way noxeval runs against Nox: the evaluation tool in TypeScript checks a Java app as a black box. With the scripted model, this proves the guards and the wiring, not the behavior of a real model; the README says so.
- **Real model optional**, through a Spring profile and the app's own API key, for anyone who wants to try it.

## Tests

- Nox's tests for each guard, ported to JUnit 5: same inputs, same expected outputs.
- **Chunking test for `StreamGuard`**: for each marker and a set of answers, every way of splitting the text into chunks (seeded random splits, a few thousand per run) must give the same result: no character of a marker is ever released, and a clean answer is released whole. This is what streaming breaks, so it is tested directly.
- `noxguard-reactor` tested with `StepVerifier`: cancellation on trip, one guard per subscription, `Replace` on a foreign link.
- CI on every push: build and tests on Java 21 and 25; the example and its noxeval suite on 25.

## Review before release (2026-10-04)

An independent review of the core, with a 20,000-case differential fuzz against the TypeScript originals and every split of 11 answers against 5 marker sets, found no way to make `StreamGuard` release a marker character. It found eight other problems, all fixed with tests: Unicode spaces joining links, three ways around the old tag removal plus its quadratic time, `StrictSchema` not making optional fields nullable and not copying deeply, a lone surrogate letting two texts share a signature, an exact-length answer marked as cut, two Javadoc claims that were not true, and two whitespace characters splitting differently from JavaScript.

## Known limits (stated in the README)

- The stream guard catches literal markers only. A paraphrased leak passes; the defense there is having no secret in the prompt.
- Links are checked at the end of the stream, so a link's text can be shown before the answer is replaced. Clients should render answers as plain text until the stream ends.
- `InputViews` gives a classifier better input; it is not a classifier.
- A guard proves nothing about a model. The proposal gate makes the model's mistake harmless; how often the model makes it is measured with noxeval.

## Out of scope for 0.1

- An input classifier port (`InputClassifier`) and a combinator with explicit fail-open or fail-closed behavior: v0.2.
- Quotas and a cost circuit breaker (they need storage, such as Redis).
- PII, toxicity and secrets detection: existing libraries do this.
- Adapters for LangChain4j and a Spring AI advisor.
