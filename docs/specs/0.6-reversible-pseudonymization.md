# noxguard 0.6 (draft): reversible pseudonymization before the model

Status: **draft**. The direction was approved by Marcus (2026-10-10, decision 3 of the Havr.IA guardrails spec): a module of its own, with the Brazilian formats as a ready-made set. The details below wait for his review. It is built together with Havr.IA's queue 6 (masking), which is its first user.

## Why

An app that sends personal data to a model provider has to replace that data before it leaves (LGPD, GDPR), and put it back before the answer reaches the user. Every team writes this by hand. The hand-written versions usually get the same things wrong:

1. **Masking too much.** Turning every number into a placeholder destroys what the model needs. In a legal app, article numbers, dates, deadlines and amounts are the substance of the answer, not personal data.
2. **No normalization.** `123.456.789-09` and `12345678909` are the same CPF. Without normalizing first, they become two pseudonyms, and search over masked text fails.
3. **Generic placeholders.** `[CPF]` everywhere means the model can't tell two people apart, and a search for one case number finds all of them. A stable pseudonym per value (`PROC_7f3a`) keeps the structure.
4. **Keys mixed across tenants.** The same CPF in two tenants must not produce the same pseudonym, or one tenant's data links to another's.
5. **Putting the data back for the wrong person.** The answer comes back with `PROC_7f3a`. Only someone who may see that case gets the real number.

## The idea

```text
text ──► find (formats + tenant dictionary) ──► normalize ──► HMAC(tenant key) ──► PROC_7f3a
                                                                     │
                                                         re-identification store (app)
answer with PROC_7f3a ──► look up (with the viewer's permission) ──► real value, or kept masked
```

- **Recognizers** find candidate values. Each one has a type, a pattern, a normalizer and, where the format has one, a check digit. A failed check digit means "not this type", so a random 11-digit number is not taken for a CPF.
- **Pseudonym** = type prefix + the first characters of `HMAC-SHA256(tenantKey, type + ":" + normalizedValue)`, in base32. The tenant key is per tenant, so the same value gives different pseudonyms in different tenants. The length grows on a collision inside a tenant.
- **No I/O in the library.** Keys come from a `KeyProvider` port; the pseudonym → value mapping goes to a `ReidentificationStore` port. The app implements both (a vault or KMS, a table with row-level security). Same rule as the rest of noxguard: pure code, the app owns storage.

## Brazilian set (`BrazilianIdentifiers.all()`)

| Type | Prefix | Format and check |
| --- | --- | --- |
| CPF | `CPF_` | 11 digits, with or without punctuation; two check digits, mod 11 |
| CNPJ | `CNPJ_` | Numeric (14 digits) and the **alphanumeric CNPJ** in force since July 2026 (12 letters or digits + 2 check digits, from ASCII value minus 48, mod 11). Both, from day one |
| Case number (CNJ) | `PROC_` | `NNNNNNN-DD.AAAA.J.TR.OOOO`, with or without punctuation; check digits mod 97 (CNJ Resolution 65/2008) |
| OAB | `OAB_` | State + number (`OAB/RJ 123.456`, `123456/RJ`) |
| E-mail | `EMAIL_` | Lowercased before the HMAC |
| Phone | `TEL_` | Brazilian numbers, normalized to digits with the country code |
| Names | `PESSOA_` | **Not by pattern.** Names come from a dictionary the app gives per tenant (its clients and parties). Matching ignores case and accents. A model-based name finder is left for later |

**Never masked:** articles, laws, sumulas, dates, deadlines and amounts. A test checks that a paragraph full of them comes out unchanged.

Other countries plug their own recognizers. The library ships only the Brazilian set, because that's the one with a real user and real test data.

## Crypto-shredding

The data protection officer's requirement (Havrus, issue #296): deleting a person's key must make their data unreadable everywhere, including old backups, without rewriting them.

- The **re-identification entries** are encrypted with a **per-subject data key** (envelope encryption). That key is itself encrypted by a master key in the KMS.
- Deleting the subject's key makes their pseudonyms impossible to reverse: in the live store, in old backups, and in anything already sent to a provider or indexed.
- **The keys must not live in the same backup as the data.** A restored backup that carries the deleted key brings the person back. This is why `KeyProvider` is a port: keys belong in a KMS or vault, with their own short retention.
- The HMAC key stays **per tenant**, not per subject. Search needs the same pseudonym for the same value across documents, and a per-subject HMAC key would require knowing the subject before finding them.

## Out of scope

- Detecting personal data in free text by model (NER).
- Anonymization. A pseudonym that can be reversed is still personal data under LGPD and GDPR. The README has to say so plainly.
- Storage, KMS clients, database tables: the app's side of the ports.

## Open questions for Marcus

1. Should the pseudonym length be fixed (simpler to test) or grow on a collision (shorter on average)?
2. Is a subject's key per person (CPF) or per client of the tenant? This decides what "delete me" erases when a person is a client of two firms.
3. Should the module be `noxguard-pseudonym`, a separate artifact, so apps that don't need it don't carry the Brazilian tables?

## Acceptance (to complete after review)

1. `123.456.789-09` and `12345678909` give the same pseudonym in one tenant, and different pseudonyms across two tenants.
2. A number with a wrong check digit is left unchanged.
3. "art. 49 do CDC, prazo de 7 dias, R$ 1.200,00, Súmula 297" comes out unchanged.
4. A numeric CNPJ and an alphanumeric CNPJ are both found and checked.
5. Reversal without permission keeps the pseudonym; with permission, it gives the original text.
6. After the subject key is deleted, reversal fails closed (the pseudonym stays), and the test proves it with a "restored backup" of the store.
