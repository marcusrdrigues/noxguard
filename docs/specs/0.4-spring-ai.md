# noxguard 0.4: a Spring AI adapter for the tool policy

Status: approved by Marcus (2026-10-06). Additive: no 0.1 to 0.3 signature changes.

## Why

`ToolPolicy` decides each tool call, but every Spring AI app has to wire it into the tool loop by hand: parse the model's JSON, ask the session, run the tool or return the denial, and get a new session per answer. Spring AI is where most Java teams call models, so most of them would write the same decorator.

One already exists. In [dio-spring-boot-learning-track](https://github.com/marcusrdrigues/dio-spring-boot-learning-track/tree/main/05-spring-ai), a voice budgeting assistant, `GuardedToolCallback` wraps each Spring AI `ToolCallback` with the policy, and `GuardedTools` gives each answer its own session and refuses to start when a tool reaches the model without a rule. It works: asked to record five expenses in one message, the fourth and fifth calls were denied with `LIMIT`. This version turns it into a module, with the five things a library can't leave the way an app can:

1. **`Confirm`.** The app denies it, because a voice flow has no screen to ask on. A library can't decide that silently: the app chooses, as with `FailureMode` in 0.3.
2. **Invalid JSON.** The app counts it with `session.decide(ToolCall.of(name))`. That works by accident: for a tool with no required argument the decision is `Run` (and uses one of the tool's calls), for a `confirm()` tool it is `Confirm`. The core needs an explicit call.
3. **Logs.** The app logs with SLF4J. noxguard depends on nothing; the app gets each decision and logs or counts it its own way.
4. **One session per answer.** The app must remember to call `forNewAnswer()` on every request. The module keeps that API and makes a misuse fail closed, not open (see "Session per answer").
5. **Spring AI version.** The app is on 2.0.0-M4. The module compiles against the 2.0 GA line and leaves the version to the app.

## Core change (`noxguard-core`, package `agent`)

```java
ToolDecision.Deny deny = session.invalidArguments("get_case_study");
// counts against the answer's limit, like any call; never against the tool's own limit, since nothing ran
// "Error: the arguments are not valid JSON. Send an object with: slug."
```

- An undeclared tool gives `UNKNOWN_TOOL`; a spent answer gives `LIMIT`; otherwise `ARGUMENT` with no argument name. No new `Reason`, so no `switch` breaks.
- The message names only the declared arguments, never what the model sent.

## The module (`noxguard-spring-ai`)

```java
GuardedToolCallbacks guarded = GuardedToolCallbacks.builder(policy)
        .tools(List.of(ToolCallbacks.from(new StoreTools())))   // any Spring AI ToolCallback
        .onConfirm(ConfirmMode.HOLD)                              // required when a declared tool has confirm()
        .listener((tool, decision) -> log.info("tool={} decision={}", tool, decision))
        .build();                                                 // throws when a tool has no rule in the policy

AnswerTools answer = guarded.forNewAnswer();                      // one per request
String text = chatClient.prompt(question).toolCallbacks(answer.callbacks()).call().content();
answer.release(isRefusal(text)).ifPresent(held -> showForConfirmation(held.call()));
// later, when the user confirms: held.run()  (runs the original tool once)
```

- **Each call:** parse the arguments with Spring AI's `JsonParser`; invalid JSON goes to `invalidArguments`; otherwise `session.decide`. `Run` calls the original `ToolCallback` and returns its result. `Deny` returns `messageForModel()` and the tool does not run.
- **`ConfirmMode`**, no default when a declared tool has `confirm()`:
  - `DENY`: the model gets "this action needs the person's confirmation, which this assistant cannot ask for" (the learning-track behavior, right for voice or batch).
  - `HOLD`: the call goes into the answer's `ProposalGate`; the model gets "held for the person to review; nothing ran". `release(refused)` gives the held call only when the answer is not a refusal (the Nox rule). `HeldCall.run()` runs the original tool once.
  - With no `confirm()` tool, `onConfirm` is optional.
- **Startup check:** every tool given to the builder must be declared in the policy, or `build()` throws with the names. A tool in the policy that is never given is fine (it may be added per request).
- **Listener:** `(String tool, ToolDecision decision)`, called once per call, after the decision. Default: nothing. `decision.loggableArgs()` has only the arguments the policy lets go to logs.
- **Per-answer state** (`AnswerTools`) is not thread-safe, like `ToolSession`; `GuardedToolCallbacks` is immutable and can be a bean.

### Session per answer

`forNewAnswer()` stays the API: explicit, and visible in the code that handles a request. The misuse is registering one answer's callbacks as `defaultToolCallbacks`: every answer then shares one session. That fails closed: the shared session reaches the answer limit and every later call is denied with `LIMIT`. The README says so with the right and wrong code side by side.

Considered and turned down: carrying the session in Spring AI's `ToolContext`, so one callback bean serves every answer. Every prompt would have to pass the context, a missing context would have to be denied anyway, and the mistake would move from one visible line to a map key. Revisit if Spring AI gives tools a per-request scope.

## Spring Boot starter

With `noxguard-spring-ai` on the class path, a `ToolPolicy` bean and `ToolCallbackProvider` or `ToolCallback` beans, the starter creates a `GuardedToolCallbacks` bean from them. `noxguard.tools.on-confirm` (`deny` or `hold`) is required when a declared tool has `confirm: true`; without it the app does not start, with the property named. Each bean backs off when the app defines its own.

## Example app

The `openai` profile's `SpringAiLanguageModel` gets the store's tools through `GuardedToolCallbacks` (today it streams text only). The scripted model and its tests stay as they are; CI does not call a real model.

## Tests

- The learning-track cases ported: a declared tool runs; an undeclared one never runs; a bad argument is denied and the tool is not called; the limit stops the fifth call; invalid JSON is denied and counts; no argument value reaches a log.
- `invalidArguments`: undeclared tool, spent answer, no use of the tool's own limit, the message with declared names only.
- `ConfirmMode`: `DENY` message; `HOLD` holds, `release(true)` drops, `release(false)` gives the call, `run()` runs once; `build()` fails without a mode when a `confirm()` tool exists.
- The startup check names every undeclared tool.
- Shared session misuse fails closed (`LIMIT`), never runs more than the cap.
- Starter: the bean, the condition on the class path, `on-confirm` required and validated.

## Changes during implementation

- **No `module-info` in `noxguard-spring-ai`**, as in the starter: Spring AI's jars are automatic modules. The jar declares `Automatic-Module-Name: com.marcusrdrigues.noxguard.springai`.
- **`JsonHelper.fromJsonToMap` instead of `JsonParser`.** `JsonParser.fromJson` is deprecated for removal in Spring AI 2.0.1, and the build treats warnings as errors.
- **An answer ends at `release`.** A call that arrives after it is denied and its tool does not run, so callbacks kept by mistake can't act after the answer.
- **Decisions are synchronized per answer**, so tool calls run in parallel still count one by one. `AnswerTools.used()` gives the count for metrics.
- **`noxguard.tools.on-confirm` lives in its own record** (`NoxguardToolCallbackProperties`), so `NoxguardProperties` keeps its 0.2 constructor.
- **The example app is unchanged.** Its use case runs its own tool loop through the `LanguageModel` port, so the scripted model can misbehave on purpose and the draft becomes a `ChatEvent`. Giving the Spring AI model `GuardedToolCallbacks` would add a second loop, run by Spring AI, that CI can't exercise without a real model. The learning-track project that this module comes from is the real-world example; moving it from its own decorator to `noxguard-spring-ai` is the natural next step there.
